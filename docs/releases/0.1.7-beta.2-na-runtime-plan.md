4. **Configuration** stays in `mods/configs/driftkings/`. Do not delete it. The candidate's defaults install only when a value is missing.

### 13.4 Behaviour (as implemented)

- **Default:** `removeFog: false` in `res/configs/driftkings/default/battle_preferences.json` and in `default_values.py`. A new profile schedules nothing.
- **Activation:** an explicit change of the option in the Settings Panel to on writes `choice.json` (`removeFog: true`) and schedules the helper. The package is installed after the game is closed; a restart notice is shown.
- **Deactivation:** an explicit change to off writes `choice.json` (`removeFog: false`) and schedules removal through the helper after the game is closed. The main `driftkings.wotmod` is not changed.
- **Persistence:** `choice.json` survives sessions and profile switches. The choice is read before any automatic decision.
- **Migration:** a legacy profile value without a choice is classified (`LEGACY_MIGRATE`) and never written to `true`. The profile is not rewritten.

## 14. Optional Remove Fog: legacy consistency, baseline comparison and validation plan (final)

Owner decisions accepted: restore the approved Remove Fog as an optional feature; default OFF; activation only by an explicit user decision; `choice.json` as the explicit-choice record; standalone architecture preserved; no extension of the approved capability.

### 14.1 Legacy inconsistency: investigation and root cause

- Finding: after the restoration (section 13), a `Driftkings.RemoveFog.wotmod` installed by an earlier release could stay loaded while the setting showed OFF. The launch path never removed a package on its own, so an owned package remained in the loading path and its fog effect stayed active while the panel showed OFF. This is the inconsistency the owner identified.
- Root cause: the HEAD design (kept from the post-approval fixes) treated automatic removal at launch as unsafe, because a profile `false` could be a materialised default. The choice file removes that ambiguity: with no recorded choice, the effective intent is OFF unambiguously.
- Resolution:
  1. Startup converges the installed state to the effective intent. With the option OFF and a verified Driftkings-owned package present, the controller schedules one removal through the native helper. The helper runs after the game closes and the player is told a restart is needed (`UI_fog_restart_off`).
  2. The native helper now keeps a **recovery copy** before deleting the package: `mods/configs/driftkings/cache/fog/recovery/Driftkings.RemoveFog-<UTC timestamp>.wotmod`. The copy is outside every mod-loading folder and is never deleted by the code.
  3. Ownership is verified before any action: the package must contain `meta.xml` with id `driftkings.removefog`. A foreign package at the target path causes the helper to refuse. Other mods' packages and resources are never read for action or modified.
  4. `effective_state()` reports the real state for the panel: `on` (chosen, package present), `on-package-missing` (chosen, package absent, install pending), `off` (no package), `off-package-loaded` (OFF but the package is still present until the restart). The panel's displayed value is the effective intent; while `off-package-loaded`, the restart notice stays visible.
- No reinstall: no path installs the package unless the effective intent is ON. Reloads, profile loads, the master switch, installation and updates add no work.

### 24.3 Canonical line-ending policy

**Inspection.** Before this phase, `.gitattributes` gave `eol=lf` to `*.py`, `*.json`, `*.js`, `*.css`, `*.md`, `*.yml`, `build_data/**`, `res/configs/**`, and `eol=crlf` to `*.cmd`. Of 1,141 tracked files, 996 text files were stored as LF, 4 are empty, and 141 are binary. No blob was CRLF. Of the 203 text files with no rule, most (`.as`, `.svg`, `.html`, `.wwu`, `.cs`, `.iss`, `.model`, `.visual`, `.xml`) followed `core.autocrlf`, which is why a plain checkout on this machine produced CRLF for them. The 123 historical restorations are explained by these two groups: the `eol=lf` families whose historical working copies were CRLF (113), and the unruled families whose historical copies were LF (10).

**Policy.** Canonical source format: LF for every textual production input, independent of `core.autocrlf` (checked-out files are LF for every text rule). Binary resources are never converted. ### 24.7 Corrected procedures (replaces the release-mode guidance of §22.2 and §22.3)

1. **Release mode does not accept `--isolated-output`.** The compiler rejects it outside debug prereleases. Output isolation for release builds comes from a separate worktree.
2. **Worktree.** `git worktree add --detach <short-path> <commit>`. The path must have at least two ancestors (B1) and be short enough for the marker workspace (B2). Use a unique path per build. Do not reuse a worktree that already holds build output.
3. **Toolchain.** Pass every tool explicitly, with `--python27`, `--hg`, `--flex-home`, `--mxmlc-jar`, `--playerglobal`, `--java`, `--csc`, `--rabcdasm-home`, `--reference-root` and `--game-root`, and `--expect-realm NA` for the production build. Do not rely on the machine-local file for the reference. Check with `--plan`, then compare the ten tool keys with the reference report.
4. **Inputs.** Restore `build_tools/javascript/node_modules` with `npm ci --ignore-scripts` from the tracked lockfile. Acquire the NA SWCs with `build_tools/acquire_flash_inputs.py --realm NA --build 999 --client <installed NA client> --install-tree`. Verify every recorded input hash before building.
5. **Line endings.** For a clean checkout use the committed canonical form (LF, §24.3). For the historical reproduction, restore the recorded line endings of §24.1 with hash verification and keep that procedure; it is a separate, historical procedure.
6. **Epoch.** Historical reproduction: `SOURCE_DATE_EPOCH=1794965041`. Clean release: the commit time of the built commit (`git log -1 --format=%ct`). Never reuse the historical epoch to force an old hash.
7. **Output.** The normal release output inside the worktree (`build\releases\beta\<version>`). It must not exist before the build. Historical artifacts are never written to.
8. **After the build.** `git status` must be empty for a clean release (`git.dirty` false). Record the build report, the input inventory, the tool list and the epoch. Keep the logs of failed attempts.
9. **Comparison.** Compare with the historical candidate by SHA-256, then by entry (names, order, uncompressed hashes, metadata). Classify differences as metadata-only (pyc header timestamps, SWF compile date), canonical source formatting, release metadata, functional, or unexplained.

### 24.8 Clean-checkout reproducibility (to be established by the Clean Release Build)

Two independent clean builds from the same committed revision and toolchain, in two separate worktrees, with canonical inputs and the commit-derived epoch, will be compared byte for byte. Clean-checkout reproducibility (K4b) is claimed only if both match, and then only for that revision, toolchain and epoch. The results are recorded in the clean-build evidence folder and in a later documentation commit, not in this commit.
